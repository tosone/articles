# 大模型进化史：从 Transformer 到 Agentic Engineering

<!-- summary: 大模型的发展不是一条单纯的模型参数增长曲线，而是模型能力、工程方法和公众感知三条线同时演进的结果。从 Transformer、GPT、BERT、ChatGPT、GPT-4、Claude、Gemini、LLaMA、DeepSeek 到 RAG、Human-in-the-Loop、Agentic Workflow、Harness 和 Skill 化工具，真正改变软件行业的是“智能如何被组织进工程系统”。 -->
<!-- tags: LLM, ChatGPT, Agentic Engineering, AI Engineering -->

如果把大模型的发展写成一张发布时间表，很容易得到一个线性的故事：2017 年 Transformer 出现，2020 年 GPT-3 变大，2022 年 ChatGPT 爆发，2023 年 GPT-4 让所有公司开始焦虑，2025 年 DeepSeek-R1 又把成本和开源推到台前。

这条线没错，但不够。

大模型真正改变软件行业的地方，不只是模型越来越大、跑分越来越高，而是人类逐渐学会把“语言”变成一种新的工程接口。最开始，我们只是让模型补全文本；后来，我们让它回答问题、写代码、调用工具、检索文档、执行任务；再后来，我们开始意识到：如果模型要进入真实系统，关键问题就不再是“它能不能生成答案”，而是“我们怎样定义目标、组织上下文、约束权限、验证结果”。

所以，这篇文章会按时间写，但不会只写时间。明线是 2017 到 2026 的关键节点；暗线有三条：

- 模型能力：模型从理解语言，到生成文本，到推理、看图、写代码、调用工具。
- 工程方法：开发者从写 prompt，到 vibe coding，到 context engineering，再到 spec coding 和 agentic engineering。
- 公众感知：AI 从论文里的概念，变成每个人都能使用、依赖、怀疑和管理的工具。

先给出一张压缩版地图。

## 一、2017-2019：Transformer 把语言问题改写成可扩展问题

2017 年 6 月，Google 的研究者发表《Attention Is All You Need》。这篇论文提出的 Transformer 架构，用自注意力机制取代了此前 NLP 里长期使用的 RNN/LSTM 思路。

它的重要性不只是“效果更好”，而是它把语言建模改写成了一个更适合大规模训练的问题。

RNN 的基本处理方式是顺序读入 token：

```text
  token 1 -> token 2 -> token 3 -> token 4
```

这让模型天然受限于串行计算。序列越长，越难保留远距离信息，训练也不容易充分并行。

Transformer 的注意力机制把问题改成了另一种形态：

```text
  token 1 <-> token 2 <-> token 3 <-> token 4
```

每个 token 都可以在同一层里和其他 token 建立关系。再加上位置编码，模型既能看到上下文，又能保留顺序信息。这个结构非常适合 GPU/TPU 上的大规模并行训练。

这就是后来一切故事的底座。

2018 年，两个方向开始分叉。

OpenAI 发布 GPT-1。它采用 decoder-only Transformer，用生成式预训练学习语言分布，再通过微调适配下游任务。GPT-1 只有 1.17 亿参数，放到今天看很小，但它确立了一个重要方向：先在海量文本上学通用表示，再迁移到具体任务。

同一年，Google 发布 BERT。BERT 采用 encoder-only Transformer，用 masked language model 训练双向上下文表示。它在自然语言理解任务上表现极强，成为很长一段时间里的 NLP 基线。

这两条路线有明显差异：

<!-- table-svg: llm-gpt-bert-table.svg -->
| 路线 | 代表模型            | 架构倾向     | 擅长任务             | 后续影响                     |
| ---- | ------------------- | ------------ | -------------------- | ---------------------------- |
| GPT  | GPT-1、GPT-2、GPT-3 | Decoder-only | 生成、补全、对话     | 走向 ChatGPT 和通用助手      |
| BERT | BERT、RoBERTa 等    | Encoder-only | 分类、抽取、检索理解 | 深入搜索、推荐、NLP 业务系统 |

2019 年，GPT-2 把生成能力推到公众视野。OpenAI 没有一开始就完整开放最大模型，而是以“模型可能被滥用”为理由分阶段发布。这件事当时引发了很多争议，但它第一次让主流媒体认真讨论“AI 生成文本是否会制造假新闻、垃圾内容和身份冒充”。

同一年，BERT 进入 Google Search。很多普通用户并不知道这件事，但它意味着大模型开始在真实消费产品里影响海量请求。AI 不是突然在 2022 年才有用，它在搜索、广告、推荐、翻译、内容理解里已经静悄悄地运行了很多年。

这一阶段的三条暗线可以这样看：

- 🔬 模型能力：从静态词向量和任务模型，进入上下文表示和连贯生成。
- ⚙️ 工程方法：预训练+微调成为主流，大模型还主要属于研究和平台团队。
- 👤 公众感知：普通人几乎无感，最多在新闻里看到“AI 会写假新闻”。

## 二、2020-2021：规模法则和 AI 编程的第一次落地

2020 年，OpenAI 发布 GPT-3。它有 1750 亿参数，在当时是一个非常夸张的数字。

但 GPT-3 的历史意义不是“参数最多”，而是它让 few-shot learning 变成了一个可感知的能力。以前你要让模型学会一个任务，通常要准备数据集、训练或微调；GPT-3 则可以在 prompt 里放几个例子，然后直接完成新任务。

```text
  任务说明 + 3 个例子 -> 模型继续完成同类任务
```

这让模型第一次看起来像是在“理解任务”，而不是只是在执行某个固定分类器。

背后的理论支撑是 scaling law。2020 年前后，研究者开始系统描述模型性能如何随着参数量、数据量、计算量增加而变化。这个阶段的行业共识很直接：更大的模型、更大的数据、更大的算力，会带来更强的能力，而且这种提升在相当长一段时间内可预测。

这个共识改变了产业投入方式。训练大模型不再只是学术探索，而变成资本、云计算、芯片和数据工程共同参与的大项目。

2021 年，AI 编程成为第一个强烈改变开发者日常体验的场景。OpenAI Codex 和 GitHub Copilot 让模型进入 IDE。开发者输入注释、函数名或半段代码，模型就能补全实现。

这件事的意义很大。相比写诗、写新闻、聊天，代码有几个天然适合大模型的特点：

- 训练数据规模巨大，开源代码可获得。
- 语法结构明确，错误可以运行验证。
- 开发者每天重复处理大量模式化任务。
- IDE 本身就是一个天然交互界面。

于是，开发者成为第一批真正高频使用大模型的人。

这一阶段也出现了 Prompt Engineering。它最早不像一门工程学，更像一套经验技巧：怎么写提示词、怎么给例子、怎么约束输出格式、怎么让模型少跑偏。

从今天看，Prompt Engineering 是后面所有 AI 工程范式的起点。它让自然语言第一次成为调用模型能力的接口。

这一阶段的三条暗线：

- 🔬 模型能力：few-shot 能力出现，代码生成开始可用。
- ⚙️ 工程方法：从训练模型，转向调用模型 API；Prompt 成为开发者的新接口。
- 👤 公众感知：科技圈和开发者震动，但普通人仍隔着 API、邀请码和工具门槛。

## 三、2022：ChatGPT 把大模型带到普通人面前

2022 年有三个关键技术铺垫。

第一是 InstructGPT。它通过 RLHF，也就是从人类反馈中进行强化学习，让模型更符合人的指令偏好。RLHF 的流程可以简化成三步：

```text
  人类示范好回答 -> 监督微调
  人类比较多个回答 -> 训练奖励模型
  奖励模型指导语言模型 -> 优化输出偏好
```

这件事的工程意义非常实际：模型不只是要会续写文本，还要会听指令、会拒绝危险请求、会用用户能接受的方式回答。

第二是 Chain-of-Thought。研究者发现，在复杂推理任务里，只要让模型“一步步思考”，模型的正确率就可能明显提升。这不代表模型真的像人一样思考，但它说明模型内部有一部分能力需要通过合适的输出结构释放出来。

第三是生成式图像模型的破圈。Midjourney、Stable Diffusion 等工具让普通人第一次感受到“输入一句话，生成一张图”的冲击。它扩大了公众对生成式 AI 的想象范围。

然后，2022 年 11 月 30 日，ChatGPT 发布。

ChatGPT 的模型本身不是从零开始的技术奇迹。它真正厉害的是把已有能力包进一个极低门槛的产品形态里：打开网页，输入自然语言，得到连贯回答。用户不需要理解 API、参数、temperature、prompt template，也不需要安装任何开发工具。

这就是为什么 ChatGPT 能快速破圈。它把 AI 从“研究者和开发者的工具”，变成了“每个人都能试一下的东西”。

公众第一次发现，AI 可以：

- 写邮件。
- 写代码。
- 翻译和总结文档。
- 解释概念。
- 模拟面试。
- 生成教学材料。
- 帮人整理思路。

也正是在这个阶段，幻觉、版权、作弊、职业替代、偏见、安全等问题同步进入公共讨论。

这一阶段的三条暗线：

- 🔬 模型能力：指令遵循、对话体验、多步推理被组合成可用产品。
- ⚙️ 工程方法：Prompt Engineering 从技巧变成工作流。
- 👤 公众感知：AI 第一次从新闻概念变成日常工具。

## 四、2023：GPT-4、LLaMA 和百模大战

2023 年是大模型全面进入产业竞争的一年。

3 月，OpenAI 发布 GPT-4。GPT-4 在专业考试、复杂推理、代码生成、多轮对话上明显强于 GPT-3.5，也让很多企业第一次认真考虑把大模型接入工作流。它不是一个单点产品，而是一个平台能力：ChatGPT、API、插件、企业服务、开发者生态都围绕它展开。

同一时期，Anthropic 的 Claude 进入更多人的视野。Anthropic 强调安全、可控和长文本处理。Claude 的存在让市场意识到，大模型竞争不会只有一家公司的一个接口，而会形成多模型、多路线、多产品形态的竞争。

Google 也在 2023 年加速追赶。从 Bard 到 Gemini，Google 的优势不只是模型论文积累，还有搜索、Android、Workspace、YouTube、TPU 和云基础设施。Gemini 被定义成多模态模型家族，这表明竞争维度已经不只是文本对话。

开源侧最重要的是 LLaMA。Meta 在 2023 年发布 LLaMA，第一版权重在社区传播后，引发了一轮开源大模型实验。随后 LLaMA 2 让更多商业和研究团队可以在自己的环境里部署、微调和评估模型。

LLaMA 的意义不是“开源模型立刻超过 GPT-4”，而是它改变了大模型的控制权结构。闭源模型像电网，开源模型像发电机。前者稳定强大，后者让团队可以在本地、私有云、垂直场景里拥有更多控制。

中国也在 2023 年进入密集发布期。文心一言、通义千问、ChatGLM、Kimi、MiniMax、百川、零一万物等模型和产品陆续出现。很多发布会看起来像“百模大战”，但背后其实有几条现实驱动：

- 中文语料和中文任务需要本土优化。
- 政企和金融场景需要私有化部署。
- 云厂商需要新的算力和平台增长点。
- 搜索、办公、客服、电商、内容生产都有明确落地入口。
- ChatGPT 无法直接稳定服务中国市场，国产替代成为现实需求。

这一阶段，工程侧也开始从单纯调用模型进入应用架构。RAG、向量数据库、插件、函数调用、工具调用、评估集、prompt template、上下文裁剪，开始成为大模型应用团队的日常词汇。

这里尤其要单独看 RAG。

RAG 是 Retrieval-Augmented Generation，也就是检索增强生成。它解决的不是“让模型更聪明”，而是“让模型在回答时能看到外部知识”。基础模型的参数像一本已经印刷好的书，训练完成后，它不知道你公司昨天更新的接口文档，也不知道某个团队内部约定，更不知道你的线上报错日志。RAG 的基本思路，就是在生成回答前先从知识库、文档库、代码仓库或业务系统里检索相关材料，再把这些材料作为上下文交给模型。

最简单的 RAG 流程大概是这样：

```text
  用户问题
  -> 查询改写
  -> 向量检索 / 关键词检索 / 混合检索
  -> 结果重排
  -> 拼接上下文
  -> 模型生成
  -> 引用和答案返回
```

这个流程看起来清楚，但真正落地时，每一步都可能出问题。

文档切分太粗，模型会拿到一大段噪音；切分太细，关键上下文又可能被拆散。只做向量检索，容易找语义相近但事实不相关的内容；只做关键词检索，又容易漏掉表达方式不同的材料。没有重排，排在前面的结果未必最有用。没有引用，用户无法知道回答依据来自哪里。没有权限控制，模型可能把 A 团队的私密文档回答给 B 团队。没有更新机制，删除过的制度、废弃的 API、过期的报价仍然可能被模型拿来当事实。

所以企业级 RAG 很快从一个 demo 变成一套知识工程：

- 数据接入：文档、Wiki、代码、工单、FAQ、数据库元信息从哪里来。
- 文档治理：谁负责更新、过期、归档和删除。
- 切分策略：按标题、段落、代码块、表格、接口定义还是业务实体切。
- 索引策略：向量、关键词、结构化字段、知识图谱是否组合使用。
- 权限过滤：检索前过滤还是检索后过滤，如何避免越权召回。
- 引用追溯：答案里的关键事实能不能回到原文。
- 质量评估：检索召回率、答案正确率、拒答率、引用命中率怎么测。

RAG 的误区也很典型。很多团队以为“接一个向量数据库”就等于有了企业知识问答，结果模型回答仍然不稳定。原因通常不是模型不会说话，而是系统没有把正确知识、正确权限、正确版本和正确证据组织起来。

这就是 RAG 对后续工程方法的意义：它让大家第一次系统地意识到，大模型应用的核心资产不只是模型，而是围绕模型组织上下文的能力。

这一阶段的三条暗线：

- 🔬 模型能力：专业能力、多模态、长上下文和代码能力全面增强。
- ⚙️ 工程方法：RAG、插件和 API 平台成为应用标配。
- 👤 公众感知：AI 从“一个聊天网页”变成“每家公司都必须回答的战略问题”。

## 五、2024：推理、多模态和 Context Engineering

2024 年之后，大模型竞争开始从“谁的模型最大”转向更复杂的问题：谁能稳定完成真实任务。

GPT-4o 把实时多模态体验推到台前。文本、图像、语音之间的边界开始变弱，模型不再只是聊天框里的文字生成器，而更像一个可以观察、听取、回应的交互系统。

Claude 3 和 Claude 3.5 强化了长文本、代码和工具使用体验。Gemini 1.5 把长上下文窗口作为核心卖点，让用户可以把更大的文档、代码库和资料一次性放进模型。

OpenAI o1 则把“推理模型”这个方向推到主流视野。它的关键变化不是回答更快，而是愿意在回答前花更多计算做推理。也就是把 scaling law 从训练阶段延伸到推理阶段：不只训练时多花算力，回答时也可以多花算力。

这个阶段，RAG 也从 demo 走向企业知识系统。很多团队第一次意识到，把文档塞进向量库并不等于有了可靠问答系统。真正困难的是：

- 文档来源是否可信。
- chunk 切分是否合理。
- 检索结果是否覆盖关键上下文。
- 权限边界是否正确。
- 引用能不能追溯。
- 更新和删除是否及时。
- 如何评估回答质量。

于是，Context Engineering 开始变得重要。

Prompt Engineering 关注“这一句话怎么问”。Context Engineering 关注“模型完成任务前应该看到什么”。这包括系统指令、用户目标、代码文件、接口文档、日志、数据库 schema、历史决策、测试输出、检索结果和工具返回。

两者差别很大：

<!-- table-svg: llm-prompt-context-table.svg -->
| 方法                | 关注点       | 典型问题                                 |
| ------------------- | ------------ | ---------------------------------------- |
| Prompt Engineering  | 怎么问       | 这个 prompt 能不能让模型给出好答案？     |
| Context Engineering | 给什么上下文 | 模型有没有看到足够、正确、不过量的信息？ |

开发者在 2024 年逐渐发现，模型能力相同的情况下，上下文组织质量会直接决定结果质量。一个 8 分模型配上正确上下文，往往比一个 9 分模型配上混乱上下文更有用。

Context Engineering 比 Prompt Engineering 更接近传统软件工程。因为它处理的是信息边界，而不是一句话的修辞技巧。

在真实代码任务里，一个好 prompt 可能是：

```text
  修复这个登录接口的超时问题，并补充测试。
```

但一个可用的上下文包应该更具体：

```text
  目标：修复登录接口在 Redis 慢查询时的请求堆积。
  相关文件：handler、service、redis client、timeout middleware。
  约束：不能修改公共 API，不能改变错误码。
  证据：线上日志、trace、复现步骤、历史 issue。
  验证：单测、集成测试、压测指标。
  回滚：保留旧路径或配置开关。
```

这两者的差别，就是“让模型猜”与“让模型在一个明确工作台上操作”的差别。

上下文也不是越多越好。长上下文模型让我们可以一次塞进更多内容，但这不等于模型会自动理解重点。过多无关文件会稀释注意力，过期文档会制造错误事实，重复材料会让模型在冲突信息中摇摆。优秀的 Context Engineering 通常包含三件事：

- 选择：只放和任务强相关的信息。
- 结构：把目标、约束、证据、候选方案、验收方式分清楚。
- 更新：根据工具返回、测试结果和用户反馈动态调整上下文。

这也是为什么后来的 agent 工具都在做类似事情：自动搜索代码、读取局部文件、总结长文档、保留会话记忆、压缩历史上下文、把测试输出重新喂给模型。表面看是“模型更会写代码了”，实际是“系统更会给模型准备材料了”。

到了这一步，Harness 这个概念开始出现。

这里的 harness 可以理解成模型外面的执行框架。模型本身负责生成判断、计划和文本，harness 负责把它接到真实世界：读取文件、调用工具、限制权限、记录步骤、执行测试、处理失败、把结果交还给人。没有 harness 的模型像一个只能说话的顾问；有了 harness，它才可能成为一个能在工程环境里行动的系统。

一个最小的 AI 编程 harness 至少会包含：

- 上下文加载器：决定哪些文件、文档、历史记录进入上下文。
- 工具适配层：把搜索、编辑、命令执行、浏览器、数据库等能力暴露给模型。
- 状态管理：记录当前任务目标、已读信息、已改文件、失败尝试和待验证事项。
- 策略约束：限制哪些命令不能执行，哪些目录不能改，哪些操作需要确认。
- 验证循环：运行测试、读取错误、让模型修复、再次验证。
- 审计日志：保留模型做过什么，方便 review、复盘和回滚。

这解释了为什么同一个模型，在聊天网页里只能给建议，在工程工具里却能完成一个中等复杂的改动。差别不只是模型，而是模型外面有没有合适的 harness。

这一阶段的三条暗线：

- 🔬 模型能力：多模态、长上下文、复杂代码、推理能力增强。
- ⚙️ 工程方法：从 Prompt Engineering 走向 Context Engineering。
- 👤 公众感知：用户从“它好神奇”变成“它为什么又编了一个不存在的答案”。

## 六、2025：DeepSeek-R1、成本革命和 Agentic Coding

2025 年，DeepSeek-R1 成为大模型历史里的重要节点。

它的意义不只是“又一个强模型”，而是它让行业重新讨论成本结构。公开资料里，DeepSeek 因开源权重、较低训练成本、较强推理能力和较高可复现性受到广泛关注。它让很多团队意识到，推理能力不一定只能由少数闭源巨头提供。

这对产业影响很直接。

如果一个能力只有极少数公司能提供，它就是稀缺资源；如果开源模型以更低成本接近闭源模型的关键能力，它就会变成基础设施。基础设施一旦普及，真正的竞争会从“有没有模型”转向“谁能把模型用好”。

中国大模型在这个阶段的路线也更清晰：Qwen、GLM、Kimi、MiniMax、DeepSeek 等不再只是追逐发布会参数，而是在开源、长上下文、推理、代码、多模态、企业部署和应用入口之间寻找差异化。

同时，AI 编程工具发生了明显变化。

早期 Copilot 更像补全器。开发者写代码，模型在旁边猜下一段。到 Cursor、Claude Code、Cline、Continue 等工具流行后，模型开始参与更完整的任务：

```text
  读需求
  -> 搜代码
  -> 修改文件
  -> 运行测试
  -> 读取报错
  -> 再次修复
  -> 生成总结
```

这就是 Vibe Coding 流行的背景。开发者不再逐行写代码，而是描述一个目标，让模型先给出实现，再人工审查、运行和修正。

但 Vibe Coding 的问题也很快暴露：它适合探索、原型和局部改动，却不天然适合生产系统。需求不清、上下文不足、测试缺失、权限过大时，模型会很快生成一堆看似合理但难维护的代码。

所以，工程方法又往前走了一步：Spec Coding。

Spec Coding 的核心不是写更多文档，而是先把需求边界写成可执行、可检查、可协作的规格。包括：

- 目标是什么。
- 非目标是什么。
- 输入输出是什么。
- 兼容性要求是什么。
- 哪些文件可以改，哪些不能改。
- 怎么验证。
- 出错怎么回滚。

MCP 等协议的出现，也说明模型正在进入工具生态。模型不只是回答文本，而是通过标准接口访问文件、数据库、浏览器、代码仓库、工单系统和内部服务。

工具调用看起来只是“给模型接 API”，但它改变了模型的角色。没有工具时，模型只能根据已有上下文生成建议；有工具后，它可以先观察环境，再决定下一步动作。

例如一个排查线上问题的 agent，不应该直接凭经验回答“可能是缓存击穿”。更合理的流程是：

```text
  读取告警
  -> 查询最近发布
  -> 拉取相关日志
  -> 查看 trace
  -> 对比指标变化
  -> 给出候选原因
  -> 请求人确认是否继续执行回滚或扩容
```

这里每一步都不是单纯的语言生成，而是“模型判断 + 工具执行 + 新证据进入上下文”的循环。模型开始像一个调度器，工具成为它的手和眼睛。

但工具越多，系统越需要组织方式。否则每个 agent 都要重新学习一遍“怎么查日志、怎么读工单、怎么发审批、怎么改配置”，不仅重复，而且危险。于是 Skill 这个概念变得重要。

Skill 可以理解成一组封装好的、可复用的能力单元。它不是简单的一条 prompt，也不只是一个 API wrapper，而是把某类任务的知识、流程、工具、约束和输出格式组合起来。一个好的 skill 通常包含：

- 适用场景：什么时候应该使用它，什么时候不应该使用它。
- 背景知识：这个领域的术语、边界、常见坑。
- 工具清单：可以调用哪些 API、命令、浏览器或内部系统。
- 操作流程：应该先查什么，再改什么，最后怎么验证。
- 安全规则：哪些动作必须只读，哪些动作必须经过确认。
- 输出规范：结果应该怎样呈现，如何给出证据和下一步建议。

这让 agent 的能力从“临场发挥”变成“可沉淀、可复用、可审查”。在人类组织里，新人会通过 SOP、手册、脚本和平台能力完成工作；在 agent 系统里，skill 扮演的就是类似角色。它把组织知识从散落的口头经验，变成模型可调用的操作模块。

再往前一步，就是 Dynamic Workflow。

传统自动化工作流通常是静态的：

```text
  A -> B -> C -> D
```

每一步都提前写死，适合审批、定时任务、数据同步这类路径稳定的场景。大模型引入后，很多任务变成动态的：

```text
  观察当前状态
  -> 判断下一步
  -> 调用工具
  -> 根据结果改计划
  -> 必要时请求人介入
  -> 继续执行或停止
```

比如同样是“修复测试失败”，如果失败原因是快照过期，agent 可以更新测试快照；如果是类型定义变了，它应该追到接口层；如果是生产逻辑错误，它应该停下来要求人确认业务预期。这个流程不是固定 DAG，而是由状态驱动的执行循环。

Dynamic Workflow 的价值在于处理不确定性。真实工程任务经常不能在开始时写出完整路径，必须边看证据边调整方案。但它的风险也在这里：如果没有边界，模型可能一路执行下去，越改越远。所以动态工作流必须和三类机制绑定：

- 停止条件：什么时候算完成，什么时候必须停下来。
- 升级条件：什么时候需要人确认，而不是继续自动执行。
- 回滚条件：什么时候要撤销、降级、切换备用路径。

这就把 Human-in-the-Loop 推到了前台。

这一阶段的三条暗线：

- 🔬 模型能力：推理和代码能力变便宜，开源模型让更多组织可部署。
- ⚙️ 工程方法：Vibe Coding 进入日常，但 Context Engineering 和 Spec Coding 才能让它进生产。
- 👤 公众感知：AI 编程从“辅助补全”变成“能不能替我完成任务”。

## 七、2026：从模型能力到工程制度

到 2026 年，大模型已经不再只是一个聊天产品。真正的问题变成：组织如何管理模型参与工作后的复杂性。

如果一个模型只能回答问题，风险相对可控。错了就改，幻觉就提醒用户。但当模型能读写文件、执行命令、调用 API、操作数据库、提交代码、创建工单、部署服务时，它就变成了一个会产生副作用的工程参与者。

这就是 Agentic Engineering 的核心问题。

Agentic Engineering 不是“让 AI 自动替你干活”这么简单。它至少包含五个部分：

<!-- table-svg: llm-agentic-engineering-table.svg -->
| 部分       | 要解决的问题                                         |
| ---------- | ---------------------------------------------------- |
| 目标定义   | 模型到底要完成什么，不完成什么。                     |
| 上下文管理 | 模型能看到哪些文件、文档、日志和历史决策。           |
| 工具权限   | 模型能调用哪些工具，能否写文件、执行命令、访问网络。 |
| 过程观测   | 人能否看到模型做了什么、为什么这么做。               |
| 验证回滚   | 修改能否测试、审查、回滚和归责。                     |

这也是 Karpathy 那条工程范式线索的最终落点。

```text
  Prompt Engineering
  -> Vibe Coding
  -> Context Engineering
  -> Spec Coding
  -> Agentic Engineering
```

这条线不是术语游戏，而是控制权的转移过程。

Prompt Engineering 时代，人主要在问问题。Vibe Coding 时代，人开始把意图交给模型。Context Engineering 时代，人发现上下文比 prompt 更关键。Spec Coding 时代，需求、边界和验收开始成为 AI 协作的核心资产。Agentic Engineering 时代，人要管理的不只是代码，而是一个能持续行动的执行系统。

换句话说，大模型越强，软件工程越不能退化成“随便说一句，让模型试试”。越强的模型，越需要更清楚的目标、更窄的权限、更可靠的验证和更完整的记录。

Agentic 和普通自动化最大的区别，是它会在执行过程中自己选择路径。

普通脚本的行为边界由代码写死。输入符合预期，它就按固定逻辑跑；输入不符合预期，它就失败。Agentic 系统不一样。它可以看到当前状态，生成计划，调用工具，再根据工具结果更新计划。这让它适合处理开放任务，比如：

- 在一个陌生代码库里实现功能。
- 根据线上症状定位可能的根因。
- 阅读大量文档后整理迁移方案。
- 组合多个内部系统完成跨部门流程。
- 对复杂表格、合同、需求文档做结构化处理。

这些任务的共同点是：路径在开始时并不完全确定。人类工程师也是边看代码、边运行测试、边缩小范围。Agentic 系统试图把这种“观察、判断、行动、再观察”的循环自动化。

但 agentic 不等于 autonomous。一个能行动的 agent 并不应该在所有事情上自动到底。越是靠近生产系统、用户数据、资金、权限、发布和外部通信，越需要 Human-in-the-Loop。

Human-in-the-Loop 不是把人放在最后点一下“同意”。它应该被设计成多层控制点：

- 目标确认：任务开始前，人确认目标、非目标和验收标准。
- 计划审查：执行复杂任务前，人看一眼模型准备怎么做。
- 权限提升：从只读到写文件、从本地到线上、从测试到生产，需要明确授权。
- 关键决策：当模型发现多种解释或业务含义不确定时，必须让人选。
- 结果验收：模型交付后，人或自动化系统验证结果是否满足要求。
- 事后复盘：失败案例进入评估集、规则库或 skill 更新，而不是只在聊天记录里消失。

很多团队对 Human-in-the-Loop 的理解太浅，只在高风险动作前加一个确认按钮。这当然有用，但还不够。真正有效的人类介入，应该发生在信息不完整、价值判断不明确、风险不可逆、成本较高的地方。

举一个代码变更的例子。模型准备修改一个核心鉴权模块时，合理的 Human-in-the-Loop 不只是“是否允许写文件”。更好的流程应该是：

```text
  模型总结现有鉴权路径
  -> 人确认理解是否正确
  -> 模型提出两种改法和风险
  -> 人选择兼容性更好的方案
  -> 模型实施最小改动
  -> 自动测试和静态检查
  -> 人 review diff
  -> 合并前保留回滚说明
```

这比“让模型直接改完再看”慢一点，但更接近真实工程系统需要的控制方式。

从这个角度看，Agentic Engineering 是几件事的组合：

- RAG 提供外部知识。
- Context Engineering 决定模型看到什么。
- Harness 让模型能安全地调用工具。
- Skill 把组织经验封装成可复用能力。
- Dynamic Workflow 让任务路径可以根据状态调整。
- Human-in-the-Loop 把判断权、授权权和责任边界放回人类流程。
- Eval 和测试系统负责判断结果是否真的可用。

少了任何一环，系统都容易退化。只有 RAG，可能只是会引用文档的聊天机器人；只有工具调用，可能是一个危险的自动化脚本；只有 Agent，没有 harness 和权限边界，容易制造不可控副作用；只有 Human-in-the-Loop，没有清晰证据和评估，人也只能凭感觉点确认。

所以，2026 年真正成熟的不是“某个 agent 一次演示能完成多炫的任务”，而是组织开始用工程制度约束它：哪些任务可以自动执行，哪些任务必须审批，哪些结果必须测试，哪些失败必须进入评估集，哪些 skill 可以被复用，哪些权限永远不能交给模型。

这一阶段的三条暗线：

- 🔬 模型能力：从回答问题走向执行长任务。
- ⚙️ 工程方法：Spec Coding 和 Agentic Engineering 成为新的工程纪律。
- 👤 公众感知：AI 不再只是工具，更像一个需要管理的协作者。

## 八、中国大模型发展全景

中国大模型的发展不能只用“追赶 OpenAI”来概括。

更准确地说，它有自己的产业约束和机会：中文语料、监管要求、私有化部署、云厂商生态、超级 App 入口、企业协同工具、成本敏感市场，以及大量愿意尝试 AI 的应用场景。

可以粗略分成三个阶段：

<!-- table-svg: llm-china-phases-table.svg -->
| 阶段         | 时间      | 特征                                                     |
| ------------ | --------- | -------------------------------------------------------- |
| 追赶期       | 2023      | 大厂和创业公司密集发布通用大模型。                       |
| 应用期       | 2024      | 长上下文、办公、搜索、客服、教育、代码等场景落地。       |
| 成本与开源期 | 2025-2026 | DeepSeek、Qwen、GLM 等推动开源、低成本推理和私有化部署。 |

几个主要玩家可以放在同一张图里看：

中国路线最有意思的地方，是它很快从模型参数竞争转向了“能不能便宜地用起来”。这和市场结构有关：大量企业客户不只关心模型能力，还关心部署成本、数据是否出域、是否能接入已有流程、是否能在中文业务场景里稳定工作。

DeepSeek-R1 的冲击就在这里。它让开源推理模型获得了全球关注，也让很多公司重新计算模型应用的成本账。过去一些只有闭源 API 才能做的事情，开始可以在开源权重、私有部署、较低推理成本的组合里被重新评估。

这不意味着闭源模型失去优势。闭源前沿模型仍然在综合能力、产品体验、工具生态、安全团队和基础设施上有明显积累。但开源模型改变了谈判结构：企业不再只能买一个黑盒 API，而是可以选择本地部署、微调、蒸馏、混合路由和多模型架构。

中国大模型的长期价值，可能不在“谁第一个超过 GPT-4/5”，而在能否把模型、云、数据、应用和行业流程整合成可持续的工程系统。

## 九、三条隐藏脉络复盘

第一条是模型能力。

```text
  语言表示
  -> 文本生成
  -> few-shot 泛化
  -> 指令遵循
  -> 多模态
  -> 复杂推理
  -> 工具使用
  -> 长任务执行
```

这条线告诉我们，大模型不是突然变聪明的。每次能力跃迁背后都有多个因素：架构、数据、规模、训练方法、对齐方式、推理计算和产品接口。

第二条是工程方法。

```text
  Prompt Engineering
  -> Vibe Coding
  -> Context Engineering
  -> Spec Coding
  -> Agentic Engineering
```

这条线对开发者更重要。因为模型能力会继续变强，但组织能否用好模型，取决于工程方法是否跟上。

Prompt Engineering 解决“怎么问”。Vibe Coding 解决“怎么快速把想法变成代码”。Context Engineering 解决“模型应该看到什么”。Spec Coding 解决“需求和验收怎么成为模型可执行的输入”。Agentic Engineering 解决“当模型能行动时，权限、观测、测试和回滚怎么管理”。

第三条是公众感知。

```text
  看不见
  -> 新奇
  -> 震撼
  -> 焦虑
  -> 依赖
  -> 挑剔
  -> 制度化
```

公众最初看到的是奇观：AI 会写诗、会画图、会聊天。随后看到的是威胁：会不会替代工作、会不会作弊、会不会生成假新闻。再往后，用户开始变得务实：它能不能稳定、能不能便宜、能不能接入我的系统、能不能对结果负责。

大模型真正成熟的标志，不是所有人都惊呼它很聪明，而是大家开始用普通工程系统的标准要求它。

## 十、给开发者和团队的实践清单

如果你是开发者，理解大模型历史不是为了背年份，而是为了判断该把精力放在哪里。

<!-- table-svg: llm-practice-checklist-table.svg -->
| 关注点   | 建议                                                                 |
| -------- | -------------------------------------------------------------------- |
| 模型选择 | 不要只看榜单，按任务、上下文长度、成本、延迟、部署边界和工具能力选。 |
| RAG      | 不要把向量库当万能解法，先管理文档质量、权限、更新和评估集。         |
| AI 编程  | 不要只让模型“改一下”，给它目标、上下文、约束和验收标准。             |
| Agent    | 不要默认授予写文件、执行命令、访问网络和生产系统权限。               |
| 评估     | 为关键任务建立样例集、回归测试和人工抽检机制。                       |
| 成本     | 区分训练成本、推理成本、上下文成本和失败重试成本。                   |
| 安全     | 把提示词、上下文、工具调用、凭证和日志都纳入安全边界。               |
| 组织协作 | 把 spec、review、测试、回滚流程前置，不要让模型绕过工程纪律。        |

最现实的路径不是“全公司立刻 Agent 化”，而是从低风险、高重复、可验证的任务开始：

1. 文档总结、日志归纳、测试生成、迁移草案。
2. 有明确边界的代码修改。
3. 有自动测试覆盖的重构。
4. 只读权限的内部知识问答。
5. 经过审批的工具调用。
6. 能回滚、能审计的自动化工作流。

如果团队准备把这些能力真正放进研发体系，可以按四层来建设。

第一层是只读知识层。先做 RAG，但不要急着追求“全知识库问答”。更稳的方式是选一个边界清楚的领域，比如发布流程、某个 SDK、某个业务系统的 FAQ，建立一套小而干净的语料。每条答案都要求引用原文，所有高频失败问题都进入评估集。这个阶段的目标不是让 AI 无所不知，而是验证文档治理、权限过滤和引用追溯能不能跑通。

第二层是辅助执行层。让模型接入只读工具，比如代码搜索、日志查询、文档读取、指标查询。此时 harness 的重点是记录和复现：模型查了什么、用了什么证据、为什么得出这个判断。输出不能只是结论，还要包含证据链。对工程团队来说，这一层已经能显著减少“先翻半小时资料”的成本。

第三层是受控写入层。允许 agent 在有限范围内改文件、生成测试、创建草稿、发起审批，但每一种写入都要有边界。比如只能改当前分支，不能碰生产配置；只能创建草稿，不能直接发邮件；只能生成回滚方案，不能自动执行回滚。这个阶段最重要的不是模型能改多少，而是所有修改都能 diff、review、test、rollback。

第四层才是动态工作流层。模型可以根据中间结果选择下一步：测试失败就读错误，日志不够就补查指标，权限不足就请求授权，发现风险就停止。这一层必须绑定 Human-in-the-Loop 和审计系统，否则很容易从“智能工作流”变成“不知道它为什么做了这些事”的黑盒自动化。

一个成熟系统最后应该能回答几个朴素问题：

- 模型为什么看到了这些上下文，而不是别的上下文？
- 它调用了哪些工具，每次工具返回了什么？
- 哪些动作是自动完成的，哪些动作经过人确认？
- 结果是否经过测试、评估或人工验收？
- 如果这次失败了，失败样例会不会进入下一轮改进？
- 这个流程能不能被沉淀成一个 skill，而不是下次重新写 prompt？

这些问题听起来不酷，但它们决定了大模型应用能不能从演示走向制度化使用。

大模型越像同事，越要纳入同事一样的流程：需求要清楚，权限要最小，变更要审查，结果要验证。

## 结语：下一阶段不是更会聊天，而是更会进入工程系统

回看 2017 到 2026，大模型的发展可以分成两个大阶段。

第一个阶段，是模型能力从无到有。Transformer 让训练可扩展，GPT 和 BERT 建立预训练范式，GPT-3 验证 scaling law，ChatGPT 证明对话产品可以引爆社会认知，GPT-4 和 Claude 把能力推向专业任务。

第二个阶段，是人类学习如何组织这种能力。RAG、工具调用、长上下文、推理模型、开源部署、Spec Coding、Agentic Engineering，本质上都在回答同一个问题：一个会生成、会推理、会调用工具的模型，怎样才能可靠地进入真实系统？

所以，大模型历史不是一部“更大参数”的历史，而是一部“智能被工程化”的历史。

未来真正稀缺的，可能不只是更强的模型，而是能把模型、上下文、工具、权限、评估和组织流程组合起来的人。模型会越来越便宜，调用会越来越简单，但把它用成可靠系统，仍然是工程问题。
